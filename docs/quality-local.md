## v0.13.0:P1 页面上下文自动偏置(搜索引擎"会话消歧"的本地版)

- content.js `contextTerms()`:焦点输入框已有文字(权重 3)+ 页面标题
  (权重 2)→ CJK 连续段 2-8 字 / 拉丁词元 2-20 位,加权 top 20,随
  GET_CONTEXT 上报(本机使用,不上传)
- offscreen:上下文词进 `recognition.phrases`(与词典目标词合并,上限
  120 条)与融合打分(+1/条,优先级低于词典、高于词频)
- 效果:在聊某个主题的页面说该主题的词汇,识别与候选选择自动偏向

## v0.13.0:P2 词频重排(IME 词频解码的本地版)

- 数据:`vendor/freq-zh60k.txt`——jieba dict.txt(MIT)按频降序前 6 万
  纯 CJK 词(494KB),`tools/build_freq_zh.py` 可重复构建;行号即名次
- 加载:offscreen 首次 ASR_START 懒加载;**>1000 条完整性守卫**,失败
  (文件缺失/损坏)自动退化为词典+上下文模式
- 打分:`freqScore` = 贪心最长匹配覆盖率×2 + 长词加权(值域约 [0,3])
- 融合决策升级为三级字典序比较:
  `词典(±2/条) > 上下文(+1/条) > 词频(需 0.35 显著边际)`
  频率分量单独触发换选需显著优势(统计噪声防护);任一高级信号分出
  胜负立即定局,平票保持主候选——不做概率性改写

# v0.12.0:质量三件套(识别偏置、候选融合、本地组织)

> 2026-11-02。用户真机反馈:稳定性清零后,剩余短板是"识别、纠错、组织能力"。
> 本版三个特性全部纯本地,不改变隐私定位。

## 短板归因

| 短板 | 卡点 |
|---|---|
| 识别 | 识别器是 Chrome 内置 Google 服务端 ASR,模型不可换(本地 Whisper/WASM 中文质量大概率更差) |
| 纠错 | macbert4csc 只做同音字级替换;Gemini Nano 深度整理被中文白名单挡死(见 v0.11.2 文档) |
| 组织 | 中文路径只有神经标点+规则,无口癖清理、无分段 |

## 实现

### 1. 识别器级热词偏置(`recognition.phrases`)

实测 Chrome 156 桌面版已支持 `SpeechRecognitionPhrase` 与 `phrases` 数组。
词典目标词(`to`,2-20 字,去重,上限 100 条)在 `start()` 时写入识别器,
**解码阶段**就偏向领域词汇——从"识别错了再替换"升级为"识别时就偏向"。
特性探测失败(旧浏览器)静默跳过,post-hoc 替换与候选融合不受影响。

### 2. 候选融合(词典投票)

识别器每句给最多 3 个候选(`maxAlternatives=3`,此前只取第一个、
候选仅供已停用的 AI 整理)。现在在 stop() 快照时对每段做投票:
`score = Σ(命中目标词 +2 / 命中已知错形 -2)`,**严格更优才换主候选**,
平票不动、无词典空操作——不引入任何概率性改写,词典为空时零行为变化。

### 3. 本地组织规则(organize)

两步、全部保守:

- **defill(口癖清理)**:只删无歧义的独立填充词(嗯/呃/噢/喔/诶/唉,
  可叠用如"嗯嗯"),须前为句首或标点;填充词自带的逗号/句号一并丢弃,
  边界标点保留。**刻意不动"那个/这个/就是"**——可作指示词/连词,
  机械删除会改坏句子("我就要这个"→"我就要")。
- **reflow(分段)**:以小句(含逗号边界)计数,当前段满 3 小句且 ≥60 字
  (或 ≥120 字)时断段;**段尾逗号升格为句号**(段落边界即句子完结,
  人类编辑的标准做法);口述"换行"处重置计数;≤3 小句不分段。
  单行输入框的 `\n` 由 content script 压成空格(搜索框不支持换行);
  textarea 保留换行;contenteditable 的换行会被 execCommand 折叠
  (浏览器限制,文字无损)。

组织只在**最终提交**时应用,实时预览不套——避免浮层文字抖动。

## 验证

- 确定性 harness 25/25(新增 F 融合换选/G 无词典不动/H 组织全链路/I 热词写入+单字过滤)
- 单元:defill 7 例(含指示词/连词反例)、reflow 真实长度分段
- 浏览器:三类输入框换行行为(input→空格/textarea→保留/ce→折叠)

## 明确未做

- 云端深度整理(OpenAI 兼容端点,用户已表态暂不做,保持纯本地定位)
- 词法级候选重排需要语言模型,当前词典投票是有意保守的折中

# v0.14.0:LLM 式序列级重排(字级 n-gram + 段级格架束搜索)

> 2026-11-02。用户提出的方向:每个人说话有口音/念错,应通过概率推算
> 前后,最终交付通顺句子。这正是 LLM 的核心机制——下一 token 条件
> 概率——的最小本地化。

## 设计

- **段级格架束搜索**:识别器每句 ≤3 候选排成格架,路径 =
  各段候选的一种组合;路径总分 = LM 对数似然 + 3.0×词典 + 1.5×上下文。
  束宽 8;最优路径须比"全主候选默认路径"高 1.5 对数单位才换选。
  与逐段独立投票的本质区别:前文的选择改变后文的条件概率上下文。
- **字级 n-gram LM**:P(c|abc)→P(c|ab)→P(c|a)→P(c) 四级 stupid
  backoff(折扣 0.4);vendor/ngram-zh.txt 14MB(1/2/3/4 元各
  12k/80k/300k/450k 条);m4.size>100k 完整性守卫;失败退化词典+上下文。

## 语料与打分的三个坑(实测钉死,后人免踩)

1. **zh 维基繁简混写**:简体计数被繁体分流("数字"一半写作"數字"),
   必须 OpenCC t2s 归一后再统计。
2. **回退链必须闭环到一元**:低阶用真实条件概率 P(c|a)=cnt(ac)/cnt(a),
   而非常数。否则高阶(3/4-gram)未收录的判别点("数字/树的")在低阶
   全落同一常数,LM 完全失去分辨力——首版实测"树的"竟胜"数字"。
3. **语体必须匹配**:维基单用时,"数字人民币"这类口说/新闻词覆盖极弱
   (百科文体里"数字"频次仅为新闻文体的零头)。主语料换 chinese-c4
   (CC BY 4.0,网络文本)+ 维基补充后,用户实测案例("币安"等)全部
   胜出,整句路径差 10.2 对数单位。

## 验证

- 用户案例逐字复现:错误路径 vs 正确路径 LM 差 10.2(门槛 1.5)✓
- harness 32/32(K1 LM 换选 / K2 无差异不换 / L 尾字恢复等 14 场景)
- 测试桩教训:填充行缺频次字段→解析全跳→守卫拦截→LM 未启用
  (表现为主候选不变);桩必须与生产格式完全一致
